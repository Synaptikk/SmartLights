# PART A - iOS platform facts

## A1. Local network access, Bonjour, UDP broadcast, multicast entitlement

**Authoritative source: Apple TN3179 "Understanding local network privacy" (rev. 2026-10-06).** https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy

Key facts (quoted/paraphrased from TN3179):

- Local network = any IP network on a broadcast-capable interface (Wi-Fi, Ethernet; not cellular/VPN). "All multicast addresses (224.0.0.0/4, ff00::/8) and the IPv4 broadcast address (255.255.255.255) are local network addresses."
- Operations that need the Local Network privilege: outgoing TCP, sending UDP unicast/multicast/broadcast, *connecting* a UDP socket, **receiving** UDP multicast/broadcast. Receiving UDP unicast and accepting incoming TCP do **not**. Checks are "deep in the networking stack" so they apply to Network.framework, BSD sockets, URLSession alike.
- All Bonjour operations (register/browse/resolve) need local network access. Resolving `.local` names needs it.
- `NSLocalNetworkUsageDescription` must be in the **app's** Info.plist (not the extension's). `NSBonjourServices` must list every service type you browse for; browsing an unlisted type (or `_services._dns-sd._udp`) requires the multicast entitlement.
- **Multicast entitlement (`com.apple.developer.networking.multicast`)**: "Your app must have this entitlement to send or receive IP multicast or broadcast on iOS. It also allows your app to browse and advertise arbitrary Bonjour service types. This entitlement requires permission from Apple." iOS 14+. Request at https://developer.apple.com/contact/request/networking-multicast . Entitlement doc: https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.multicast . TN3179 table: sending/receiving UDP **broadcast** = entitlement required; unicast = not required. Not required on macOS.
  - Practical: the request form asks for an App Store URL; a DTS engineer suggested entering "N/A" with an explanation; approvals have been reported in ~5 business days. Sources: https://developer.apple.com/forums/thread/670458 , https://developer.apple.com/forums/thread/687122 . The entitlement is a *managed capability* assigned per team; with a **free Personal Team you cannot get it** (managed capabilities require a paid Developer Program membership) **[uncertain: inferred from Apple's capability model, not a direct quote]**.
- **Background**: if the app is in the background and the privilege is still *undetermined*, the OS silently denies the operation (no prompt, not recorded). App extensions share the container app's privilege state; background-type extensions are denied while undetermined. App Clips cannot use the local network. Simulator does not model this: test on device.
- There is no API to query or request the privilege (FB8711182). Detect denial via `NWConnection.currentPath?.unsatisfiedReason == .localNetworkDenied` or Bonjour `kDNSServiceErr_PolicyDenied` (-65570). Trick to force the prompt early: `connect()` a UDP socket to a link-local address (code in TN3179).
- iOS 18 had a state-sync bug (FB14321888) fixed in iOS 18.6.
- Historical FAQ thread (now superseded by TN3179): https://developer.apple.com/forums/thread/663858

**UDP broadcast specifics (WiZ, LIFX discovery to 255.255.255.255 / x.x.x.255):**

- Quinn (Apple DTS), "Broadcasts and Multicasts, Hints and Tips" (2025-01-16): `NWConnection` broadcast support is "useless in practice"; `NWConnectionGroup`/`NWMulticastGroup` does IPv4 multicast only and **no broadcast**. **BSD sockets are "the only option for UDP broadcast."** Create one socket per interface, bind with `IP_BOUND_IF` (do not hard-code `en0`), set `SO_BROADCAST`, prefer directed broadcast (x.x.x.255) over 255.255.255.255. Receiving can be on one socket bound to 0.0.0.0 with `SO_REUSEADDR/SO_REUSEPORT`. https://developer.apple.com/forums/thread/772642
- **iOS/iPadOS 26 regression**: broadcast via `NWConnection` to 255.255.255.255 fails with `sendmsg ... [13: Permission denied]` (EACCES) even with the multicast entitlement; Quinn (Oct 2025) called it "certainly a regression" but again said: switch to BSD sockets. https://developer.apple.com/forums/thread/805719
- Older but relevant: BSD-socket broadcasts were temporarily exempt from the entitlement in iOS 14.0-14.4; from 14.5 the entitlement is enforced for sockets too. https://developer.apple.com/forums/thread/661208 , https://developer.apple.com/forums/thread/680509

## A2. HomeKit framework (HMHomeManager) from a third-party app

- Capability: enable HomeKit in Xcode; adds `com.apple.developer.homekit` entitlement and App ID feature. Requires `NSHomeKitUsageDescription` or the app crashes on first use. Permission prompt appears when you create `HMHomeManager`; check `authorizationStatus` / `homeAccessNotAuthorized`. https://developer.apple.com/documentation/homekit/enabling-homekit-in-your-app . The HomeKit entitlement is **not** a managed/approval entitlement (any paid team, and in practice Personal Teams too, can enable it) **[Personal Team support: uncertain]**.
- **Matter accessories in Apple Home are reachable through HomeKit**: "Apps that don't implement their own Matter ecosystem can use the HomeKit API to control Matter accessories in addition to HAP accessories. A HomeKit entitlement is sufficient to access all accessories the user added to Apple Home, without having to explicitly re-pair accessories." https://developer.apple.com/apple-home/matter/
- Platform availability (Apple doc metadata): iOS 8+, iPadOS 8+, **Mac Catalyst 14+**, tvOS 10+, watchOS 2+ (independent watch apps from watchOS 7), visionOS 1+. **No native macOS (AppKit) HomeKit.** https://developer.apple.com/documentation/homekit . A Catalyst build bug in Xcode 14.0 (entitlement stripped) was fixed in 14.1. https://developer.apple.com/forums/thread/709819
- App Review: Guideline 2.5.1: "Apps should use APIs and frameworks for their intended purposes ... For example, the HomeKit framework should provide home automation services"; Guideline 5.1.2(vi): HomeKit data may not be used for marketing/advertising/data mining. https://developer.apple.com/app-store/review/guidelines/ (for a personal sideloaded app this is moot).
- **Background / widgets limitation**: HomeKit calls from an App Intent executed in the widget/control extension process fail since iOS 18.4 with `HMErrorDomain Code=80 "Missing entitlement for API" ... Handler does not support background access`; still reproduced on iOS 26 beta. Workaround that works: make the intent `ForegroundContinuableIntent` (unavailable to extensions) so it runs in the main app process. Apple DTS asked for a bug report. https://developer.apple.com/forums/thread/779354 . Older report of same code 80 from a Siri extension: https://developer.apple.com/forums/thread/649652
- Latency: HomeKit goes through `homed` to the accessory (local HAP/Matter, or via a home hub when remote). No quantitative data found; empirically comparable to Home app. **[no primary source]**
- Reading Matter devices' Matter-level details through HomeKit: HomeKit exposes them as HMAccessory/HMService; Apple also offers a "Matter tunneling" path (`home.matterControllerID` / `matterControllerXPCConnectBlock`) to send raw Matter commands through HomeKit's pairing, but `openCommissioningWindow` over that XPC path is unsupported (`MTRErrorDomain Code=6`). https://developer.apple.com/forums/thread/747438 , https://developer.apple.com/forums/thread/757458

## A3. Matter on iOS (Matter.framework + MatterSupport)

- iOS 16.1+ includes Matter; Xcode ships the certified Matter SDK ("You are encouraged to use this version of the SDK"). https://developer.apple.com/apple-home/matter/
- **Yes, a third-party app can commission into its OWN fabric without Apple Home**, but the *supported* path is the **MatterSupport** flow: your app calls `MatterAddDeviceRequest(topology:).perform()`; iOS shows the system UI, scans the QR, provisions Wi-Fi/Thread credentials, then calls your **app extension** (`MatterAddDeviceExtensionRequestHandler`, extension point `com.apple.matter.support.extension.device-setup`) with `commissionDevice(in:onboardingPayload:commissioningID:)`, where you run `MTRDeviceController.setupCommissioningSession` + `commissionNode` against your own fabric (own `MTRDeviceControllerFactory`, `MTRStorage`, IPK + root keypair stored in iCloud Keychain, CSA vendor ID). Full code: https://developer.apple.com/documentation/mattersupport/adding-matter-support-to-your-ecosystem and https://developer.apple.com/documentation/matter/onboarding-a-matter-device
- Requirements (from Apple docs + Espressif/Nordic integrations): MatterSupport extension target, App Group + Keychain Sharing between app and extension, `NSBonjourServices` for `_matter._tcp`, `_matterc._udp`, `_matterd._udp`, local-network usage string; iOS 16.4+ recommended by integrators. https://docs.rainmaker.espressif.com/docs/sdk/rainmaker-matter-sdk/Commissioning/ios-native-bridge
- `com.apple.developer.matter.allow-setup-payload` is **not** a managed entitlement (DTS, Apr 2026: "you can add it without approval ... most apps don't need it" because the system QR scanner supplies the payload). It is for adding devices without a QR code, or adding an already-paired device from your ecosystem to Apple Home. https://developer.apple.com/forums/thread/823198 , https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.matter.allow-setup-payload
- DTS (Apr 2026) on using Matter.framework *directly* (skipping MatterSupport, BLE PASE yourself): development only works with the "Bluetooth Central Matter Client Developer Mode" profile; there is **no production entitlement** for that path - use MatterSupport. https://developer.apple.com/forums/thread/823198
- The MatterSupport flow by design pairs the accessory into multiple ecosystems (Apple Home is one); after it, "your app's ecosystem has its own pairing relationship with the accessory and communicates with it directly" over IP. Whether a user can skip Apple Home entirely in that UI is **[uncertain]** (DTS said it is "unclear whether an accessory can pair with only one ecosystem").
- **Thread**: a third-party app **cannot** use the iPhone's own Thread radio. MatterSupport shows "Thread Border Router Required" when no border router exists; DTS confirmed (Nov 2024) "the device's Thread radio does not expose itself as a border router, so it is not accessible to your app or MatterSupport extension" (FB15614070). Apple Home can do hub-less Thread pairing on iPhone 15 Pro; third parties cannot. https://developer.apple.com/forums/thread/766729 . Wi-Fi Matter devices need no hub: your controller talks to them directly over the LAN.
- Does it require a HomeKit home? No; your own fabric is independent of HomeKit. Does it require the HomeKit entitlement? No.
- Useful sample code: Nordic nRF Matter for Mobile (MatterSupport + own fabric via MTRDeviceController) https://github.com/divipillai/kotlin-nrf-matter ; Espressif RainMaker iOS commissioner https://github.com/espressif/esp-rainmaker-ios/blob/master/ESPRainMaker/ESPRainMaker/Matter/Matter.md ; connectedhomeip issue showing `createController(onExistingFabric:)` then fallback `onNewFabric:` https://github.com/project-chip/connectedhomeip/issues/29537 ; forum on getting the node after commissioning https://developer.apple.com/forums/thread/756870 ; Matter alpha/blog https://farcaller.net/2023/matter-and-smart-devices/
- Alternative for Matter devices already in Apple Home: just use HomeKit (A2) - far less code, no fabric management, works for Thread devices via the user's hub.

## A4. Bluetooth (CoreBluetooth) for BLE bulbs (Hue BT, Govee BLE, Nanoleaf Essentials BT, etc.)

- Foreground scanning is unrestricted; background requires `UIBackgroundModes: bluetooth-central`, and background scans must specify service UUIDs (nil scans are foreground-only), with coalesced discovery and `CBCentralManagerOptionRestoreIdentifierKey` state restoration. The OS may still terminate the app; disconnections while suspended are only learned on resume. Sources: https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html (archived but still Apple's guidance).
- Pairing/bonding is handled by iOS when a characteristic requires encryption; you cannot initiate pairing programmatically. For Matter-over-BLE commissioning you *must* use MatterSupport (A3). No new 2025-2026 changes found affecting bulbs **[no recent source]**.
- Protocol notes: Hue BT bulbs use a proprietary GATT (reverse-engineered in community projects); Govee BLE uses vendor GATT writes; treat BLE as a fallback, Wi-Fi/Zigbee-bridge paths are far more reliable.

## A5. Background execution and "automations" on iPhone

Realistic picture (Apple-side constraints):

- **No persistent background process.** iOS suspends the app shortly after backgrounding; BGTaskScheduler gives opportunistic, short, OS-scheduled slots (not time-accurate). Keeping UDP/SSE connections alive in background is not possible except briefly. Local-network ops while backgrounded and privilege-undetermined are silently denied (TN3179).
- **Interactive widgets (iOS 17+, WWDC23 10028 "Bring widgets to life")**: Buttons/Toggles run an `AppIntent` in the widget extension process. Works fine for direct HTTP/UDP to lights (extension shares the app's Local Network privilege) but **HomeKit calls fail from the extension** (A2) unless routed to the app via `ForegroundContinuableIntent`. https://developer.apple.com/videos/play/wwdc2023/10028/
- **Control Center / Lock Screen / Action button controls (iOS 18+, WWDC24 10157 "Extend your app's controls across the system")**: `ControlWidget`, `ControlWidgetToggle`, `AppIntentControlConfiguration`. No way to show errors from a control (DTS: open the app or briefly start a Live Activity). https://developer.apple.com/videos/play/wwdc2024/10157/ , https://developer.apple.com/forums/thread/759853
- **App Intents + Siri + Shortcuts**: the best "automation" story on-device; Shortcuts personal automations (time, arrive/leave, NFC) can run your intents without user confirmation. Intents may run in-process or in the app; HomeKit intents need the app process.
- **Live Activities**: display only; can host intents (buttons) since iOS 17.
- **Apple Watch**: independent watchOS apps support HomeKit (watchOS 7+); your own UDP/HTTP code also works on watch but local-network privacy does not exist on watchOS (TN3179 table), and watch radios are power-constrained.
- **Push from a home server**: silent pushes are throttled and not for real-time control; best used to refresh widgets. The server itself (A/B3) is what should run schedules and automations; the iPhone is a remote control.

## A6. TLS to the Hue bridge and the CLIP v2 event stream

- Hue's HTTPS model: validate the bridge cert against **Signify's private root CA** (`huebridge_cacert.pem`, downloadable from the developer portal) and check the certificate **CN == bridge ID** (16-hex-char id, e.g. `001788FFFExxxxxx`); connect using the bridge ID as hostname (via your own DNS mapping) or override hostname verification. Original self-signed bridge certs were also issued with CN = bridge id. Sources (docs are login-gated; quoted by community): https://community.homey.app/t/philips-hue-dynamische-scenes-starten-met-logic-http-request/67913 , Apple forum Swift example https://developer.apple.com/forums/thread/707602
- **2025 changes you must handle**:
  - Bridge v2 firmware **1971060010 (May 22, 2025)**: "replaced self-signed certificates with proper HTTPS certificates" (issued by Signify's own CA). Signify asked integrations to **drop certificate pinning and stop accepting self-issued certs** (homebridge-hue maintainer). Old-firmware v2 bridges still present self-signed certs. https://hueblog.com/2025/05/24/philips-hue-improves-security-of-the-hue-bridge/ , https://github.com/ebaauw/homebridge-hue/issues/1219
  - **Hue Bridge Pro (BSB003)** presents a certificate chaining to a *new* Signify root CA (different from the white-bridge CA); openHAB had to add the new root; hostname must equal the bridge ID. https://github.com/openhab/openhab-addons/issues/19337
  - **HTTP is being removed**: developer portal (June 4, 2025): "Firmware releases will no longer support HTTP because of RED compliance ... The Hue API should be accessed exclusively over TLS". Bridge Pro is HTTPS-only. Digest auth for the remote API was turned off Jan 31, 2025. The *cloud* api.meethue.com moved to Google Trust Services in 2025 (that announcement is about the cloud API, not the bridge). https://developers.meethue.com/
  - Practical URLSession approach: `URLSessionDelegate.urlSession(_:didReceive:completionHandler:)` -> build `SecTrust` with anchor certificates = [old Signify root, new Signify root], `SecTrustSetAnchorCertificatesOnly(true)`, then evaluate with an `SecPolicyCreateSSL(true, bridgeId)` policy (hostname = bridge id, not IP), or evaluate with hostname disabled and compare the leaf CN to the bridge id yourself; **also accept the leaf self-signed cert whose CN == bridge id for old firmware** (TOFU pin by bridge id). Home Assistant simply disables verification; openHAB imports the roots.
- **Event stream**: `GET https://<bridge>/eventstream/clip/v2` with headers `hue-application-key: <key>`, `Accept: text/event-stream`; SSE lines `id:` and `data:` where `data` is a JSON array of `{id, creationtime, type: add|update|delete, data:[...]}`. aiohue uses a 90 s read timeout, a 60 s keepalive hack (renaming a geofence client to force an event), `last-event-id` on reconnect, and backoff `min(2*attempts, 600)` s. https://raw.githubusercontent.com/home-assistant-libs/aiohue/master/aiohue/v2/controllers/events.py
- In Swift: `URLSession.bytes(for:)` -> `AsyncBytes.lines` parses SSE trivially (WWDC21 10095); or use mattt/EventSource (spec-compliant, Swift 6). https://wwdcnotes.com/documentation/wwdc21-10095-use-asyncawait-with-urlsession/ , https://swiftpackageregistry.com/mattt/EventSource . The same custom-trust delegate applies to the streaming session. Note: iOS kills the stream when the app suspends; reconnect on foreground.
- Hue local API rate guidance (from Hue docs, general knowledge): ~10 light commands/s, 1 group command/s via CLIP v1; CLIP v2 similar. **[not re-verified this session]**

## A7. Cross-platform (Flutter / React Native) vs native Swift

- Every hard requirement here is a native-only API: Network.framework/BSD sockets with the multicast entitlement, Bonjour via `NSBonjourServices`, `HomeKit.framework` (no maintained Flutter or RN wrapper found: pub.dev "homekit" is a pure-Dart HAP implementation, 3 years old; no RN HomeKit package surfaced), `MatterSupport` + an **app extension** (Flutter's only Matter plugin, grandcentrix `flutter_matter`, was v0.0.1 and **archived Oct 27, 2025**), WidgetKit/ControlWidget/App Intents (Swift-only, run in extensions), CoreBluetooth. Sources: https://pub.dev/packages?q=homekit , https://github.com/GCX-HCI/grandcentrix-flutter-matter-plugin/blob/main/flutter_matter/README.md , https://pub.dev/packages/matter_sharing
- A Flutter/RN app would end up with 60-80 % of the logic in Swift platform channels anyway, and widgets/controls/Siri would still be Swift.
- **Recommendation: native Swift/SwiftUI**, targeting iOS 17+ (interactive widgets) or 18+ (controls). If an Android build is ever wanted, keep the protocol layer (UDP/HTTP/SSE codecs) in a platform-neutral Swift package; or put device logic on a home server (B3) and make the phone app thin.

# PART B - Hue bridge modification

## B1. Hue Bridge v2 (BSB002) rooting: what exists, what it gets you, risks

- **Method (2016, pepe2k / Colin O'Flynn)**: open the case, 3.3 V UART header (v2.1: pin1 GND, pin4 RX, pin5 TX; board may not cold-boot with TX attached). U-Boot has `bootdelay=0`, so interrupt boot by **shorting the SPI-NAND data/CS line** (remove R31 on v2.0, or probe a test point on v2.1) to drop to the U-Boot prompt; then set a U-Boot env var that the init script compares against the root password hash (`security` var), enable Dropbear `RootLogin`, open iptables for SSH. Sources: https://forum.archive.openwrt.org/viewtopic.php?id=66346 , https://colinoflynn.com/2016/07/getting-root-on-philips-hue-bridge-2-0/ , https://hackaday.com/2016/07/26/root-on-the-philips-hue-iot-bridge/ , https://blog.kleine-koenig.org/ukl/philips-hue-bridge-v21.html , https://www.jkry.org/ouluhack/HackingHueBridge , hidden Wi-Fi radio enable https://medium.com/@rxseger/enabling-the-hidden-wi-fi-radio-on-the-philips-hue-bridge-2-0-42949f0154e1
- **Most recent confirmed write-up: a 2022 HackMD note** (OpenWrt 19.07.8, kernel 4.14.241, MIPS 24kc; same NAND-short trick still worked). Inside: `ipbridge` (Zigbee, talks to the radio via `/dev/ttyZigbee` -> `ttyACM0`), `clipd` (CLIP v2), `hk_hap` (HomeKit, port 8080), `stream` (Entertainment UDP 2100), `behaviord`, `updated` (A/B boot slots), `websocketcd` (remote), `iot-connectivity` (local Mosquitto MQTT bridged to Google Cloud IoT), `provisioning` (device certs), nginx front end. U-Boot env vars for an SSH key and remote syslog **persist across firmware updates**. https://hackmd.io/@fjTXL6atTJyn_W4kMM9iCQ/SyEEzTU85
- Running custom binaries after root: https://github.com/lyuzashi/hue-platform (notes that newer firmware removed opkg).
- **What root does NOT give you**: the Zigbee coordinator is a separate MCU driven by the closed `ipbridge` daemon over a serial/USB-CDC link; nobody has published a way to run Zigbee2MQTT/ZHA on it or to add non-ZLL/Zigbee-3.0 devices. All the useful functionality (lights, scenes, events, Entertainment) is already exposed by the official local API.
- **Risks**: soldering/probing a live board; bricking (the `updated` A/B slots help, but U-Boot env mistakes do not); firmware updates may silently remove tools; security/cloud daemons will keep running; no one has published a 2023-2026 reproduction, so applicability to current firmware (1974xxxxxx, 2026) is **[uncertain]**. Signify's release notes list continual updates through Apr 2026 and say nothing about developer shells. https://www.philips-hue.com/en-us/support/release-notes/bridge
- **Conclusion**: rooting is a hobby project, not a path to a better light-control app. Nothing you would gain is needed for the iPhone app.

## B2. Hue Bridge Pro (BSB003, announced Sep 3-4 2025)

## B3. The practical alternative: full local API + an always-on home server

Your Hue bridge already exposes everything a client needs (CLIP v2 REST + SSE events, Entertainment UDP streaming, scenes, zones, sensors, Matter bridging). The question is only *where* the multi-brand glue lives.

**Architecture 1 - iPhone talks directly to each device**
- Pros: zero extra hardware; lowest latency when on the home Wi-Fi; simplest to deploy for one person; no server maintenance.
- Cons: needs the multicast entitlement + BSD sockets for WiZ/LIFX/Govee discovery; every brand's protocol (and quirks like Hue cert changes, Govee multicast flakiness) lives in the app; **no automations when the phone is asleep/away**; no state when away from home unless each brand's cloud is used (AiDot is cloud-only anyway); Thread Matter devices need a border router and can only be reached via HomeKit; widgets must re-discover devices quickly.

**Architecture 2 - iPhone talks to a home server (Raspberry Pi / Mac mini / Docker)**
- Candidates:
  - **Home Assistant** - core local integrations for Hue (local push via SSE), WiZ (local UDP), LIFX (local), Govee (`govee_light_local`), Nanoleaf panels (local TCP API), AiDot (added 2026.6: cloud login + persistent local TCP per bulb), HomeKit Device (pull HAP/Thread devices in), and a Matter controller (Matter Server add-on, needs HAOS/IPv6/mDNS, Thread devices need a border router). It can **re-export everything to Apple Home via its HomeKit Bridge** (HAP, 150 accessories per bridge instance) so Siri/Home/Control Center work without any app code. Its REST + WebSocket API is what your iPhone app would talk to (one protocol instead of eight), and automations/schedules run 24/7 on the server. Sources: https://www.home-assistant.io/integrations/wiz , https://www.home-assistant.io/integrations/lifx/ , https://home-assistant.io/integrations/govee_light_local , https://www.home-assistant.io/integrations/nanoleaf , https://www.home-assistant.io/integrations/aidot/ , https://www.home-assistant.io/integrations/homekit/ , https://www.home-assistant.io/integrations/matter/
  - **diyHue** - Python Hue-bridge emulator (API v1-style) that fronts WLED, Yeelight, MQTT, Home Assistant, Tradfri gateway, deCONZ etc. so Hue-compatible apps see one "bridge"; it does not natively list WiZ/LIFX/Govee/Nanoleaf (reach them via its Home Assistant/MQTT bridge). Useful only if you want to keep a *single Hue-style client API*. https://github.com/diyhue/diyHue ; Bifrost is a Rust alternative limited to Zigbee2MQTT devices https://neilturner.me.uk/2026/06/03/diyhue-philips-hue-bridge-emulator/
  - **Matterbridge** (Node, Luligu) - creates one Matter bridge you pair into Apple Home; `matterbridge-hass` exposes Home Assistant entities, `matterbridge-zigbee2mqtt` exposes Z2M devices; no first-party WiZ/LIFX/Govee/Nanoleaf plugins found. Good if you want everything to appear as Matter in Apple Home and then use **HomeKit.framework** as your single API on the phone. https://github.com/Luligu/matterbridge
- Pros: one API for the app; automations, schedules, presence, and event history run server-side; remote access via HA Cloud/Tailscale; Apple Home/Siri/Watch for free via HomeKit Bridge; no multicast entitlement needed on the phone (server does discovery); easier to add brands later.
- Cons: extra device to maintain; one more hop of latency (usually <50 ms on LAN); Hue Entertainment streaming should still go phone/PC -> bridge directly; some vendor features (Hue dynamic scenes, Govee DIY effects) may be flattened.

**Recommended hybrid**: Phone app with direct Hue (CLIP v2 + SSE; best-in-class) and HomeKit.framework for everything Apple Home already knows (Matter/Thread/HAP devices, plus anything a server re-exports); run Home Assistant on a Pi for WiZ/LIFX/Govee/AiDot discovery and automations and re-export those as HomeKit Bridge accessories. The app then needs **no multicast entitlement at all**, works from a free or paid account, and still gets interactive widgets/controls via HomeKit (through the app process) or HA's REST API.

## B4. Can the Hue bridge adopt third-party Zigbee bulbs?

Signify's rule: the bridge joins **Zigbee Light Link (ZLL)** and, since 2018, **Zigbee 3.0** lights; it does not join Zigbee HA (ZHA) devices. Third-party lights appear as normal lights in CLIP (so your app sees them as "Hue"), but they are **not exposed to HomeKit/Matter by the bridge**, get no firmware updates, no Entertainment/Sync support, and dimming/colour fidelity differ. https://developers.meethue.com/zigbee3 , https://hueblog.com/2021/07/08/ikeas-new-frosty-zigbee-light-bulbs-make-a-statement/ , https://thesmartcave.com/smart-bulbs-compatible-with-philips-hue/

|---|---|---|
| **IKEA Trådfri** | Yes (bulbs on firmware >= 1.2.x; reset by power-cycling 6x) | Old firmware reported ZHA profile and was rejected; Zigbee 3.0 models fine. https://androidauthority.com/add-ikea-tradfri-lights-philips-hue-1211149 |
| **Innr** | Yes, "detected the same as Hue originals" | "Works with Hue"/Friends of Hue partner. https://www.schieb.de/nutzen-von-innr-geraeten-mit-hue-bridges |

If you want *all* Zigbee gear unified, the server route (Zigbee2MQTT/ZHA with a Sonoff/ConBee coordinator) is the standard answer - and rooting the Hue bridge does not help with that.

## Bottom line

1. Build native Swift. Use HomeKit.framework for anything in Apple Home (incl. Matter/Thread), CLIP v2 + SSE for Hue (handle the 2025 CA change: trust both Signify roots + legacy self-signed by bridge-ID), and unicast UDP/HTTP for WiZ/LIFX/Govee/Nanoleaf. Broadcast/multicast discovery needs the managed multicast entitlement (paid account) **and** BSD sockets (NWConnection broadcast is broken on iOS 26).
2. Expect no real background execution; put schedules/automations on a server (Home Assistant on a Pi) and surface quick actions via interactive widgets, iOS 18 controls, and App Intents (HomeKit intents must run in the app process).
3. Do not modify the Hue bridge. Rooting (UART + NAND-short, last documented 2022, v2 only) gives a shell but no Zigbee coordinator access or anything your app cannot already get from the official local API; it risks bricking and voids updates. The Bridge Pro has no public root. Spend the effort on a home server instead.
